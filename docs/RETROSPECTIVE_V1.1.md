## 一、问题复盘（按重要度排列）

### P0 — 功能损坏（影响用户正常使用）

#### 1. 置顶贴不置顶 + 热度不衰减

| 维度 | 说明 |
|------|------|
| **现象** | 管理员置顶的文章排在列表最底部，且旧置顶贴始终 99°C 不衰减 |
| **原因** | ① `ORDER BY` 只有 `hot_score DESC, published_at DESC`，没有 `is_pinned` 作为 tiebreaker → 排序不优先，但还算不上排在"最底部"（应该是同分时才正确）；② 实际更严重的是：`PATCH /api/admin/articles/:id` 只更新了 `is_pinned` 字段，没有触发 `scoreArticle()` 重算热度 → 旧置顶贴保持 99°C 不衰减，新置顶贴也没有计算衰减热度；③ `ORDER BY` 缺少 `pinned_at DESC NULLS LAST` → 多个置顶贴之间顺序随机 |
| **解决** | ① ORDER BY 改为 `hot_score DESC, is_pinned DESC, pinned_at DESC NULLS LAST, published_at DESC`；② PATCH 处理后调用 `scoreArticle()` 重算热度；③ 添加置顶衰减公式：99(12h)→95(24h)→90(48h)→85(72h)→普通 |
| **预防** | 涉及排序的改动，必须同时检查 `ORDER BY` 子句和后置操作（PATCH 后是否要 recalc）。建议在 AGENTS.md 中显式记录排序策略 |

#### 2. stars 字段缺失导致 GitHub 历史仓库全量入库失败

| 维度 | 说明 |
|------|------|
| **现象** | 部署上线后 `gitHubHistory.ts` 全部 30 条插入报错 `column "stars" does not exist`，常青榜和新锐榜无数据 |
| **原因** | `gitHubHistory.ts` 的 `INSERT INTO articles` 包含 `stars` 字段，但 `schema.sql` 中没有定义该列。属于"代码先写，schema 后加"的时序问题 — 代码合入时忘记同步 schema 变更 |
| **解决** | `ALTER TABLE articles ADD COLUMN stars INTEGER DEFAULT 0` |
| **预防** | 新增字段时，schema.sql 和代码必须在同一 PR/commit 中同步修改。建议在开发流程中加一条：涉及 DB schema 变更时，先改 schema.sql 再写代码 |

#### 3. CORS 阻止管理端 POST 请求

| 维度 | 说明 |
|------|------|
| **现象** | 前端 `sr.miko-ai.cn` 调 `POST /api/admin/fetch` 报 `Failed to fetch`（CORS 错误），GET 请求正常 |
| **原因** | `allowedOrigins` 默认只包含 `http://localhost:5173` 和 `http://localhost:3001`，生产域名 `https://sr.miko-ai.cn` 未加入白名单。GET 是简单请求不受 CORS 限制，但 POST 需要预检 |
| **解决** | 默认值追加 `https://sr.miko-ai.cn`，同时建议 Render 环境变量 `CORS_ORIGINS` 也配置生产域名 |
| **预防** | 涉及生产部署的配置（CORS 域名、API 地址等），应在 PRD 或部署文档中显式列出，上线前检查清单中增加"后端 CORS 配置已包含生产前端域名" |

#### 4. 翻译队列 SQL 条件 AND 导致部分文章漏翻

| 维度 | 说明 |
|------|------|
| **现象** | `WHERE title_zh = '' AND summary_zh = ''` 要求两个字段同时为空才处理。如果 title_zh 已翻译但 summary_zh 翻译失败（留空），文章不会再被扫描 |
| **原因** | 初始设计时用 `''` 表示"未处理"，但无法区分"未处理"和"已处理但无需翻译"。AND 条件过于严格 |
| **解决** | 改用 NULL 语义：`WHERE title_zh IS NULL OR summary_zh IS NULL`。NULL=未处理，''=已处理/无需翻译，非空=已翻译 |
| **预防** | 状态字段设计时先明确状态空间：有几种状态？分别用什么值表示？是否有歧义？建议用 NULL/NOT NULL 做二值状态判断 |

### P1 — 内容质量（影响用户留存）

#### 5. Hacker News 内容质量差（无摘要 + 非 AI 内容）

| 维度 | 说明 |
|------|------|
| **现象** | ① HN 文章全部没有摘要，卡片显示空白；② 大量非 AI 内容（政治、经济、生活）混入 |
| **原因** | ① HN RSS 的 `<description>` 只包含 `Comments` 链接，无实际摘要内容 — parseRSS 提取了无意义的 HTML；② 最初没有 AI 内容过滤，HN 是综合社区 |
| **解决** | ① 检测到 summary 为 "Comments" 时置空；② 添加 AI 关键词白名单过滤 |
| **预防** | 新增数据源时，必须先确认该源的 RSS/API 返回格式，检查是否存在同类型的数据质量问题（空字段、噪音内容）。建议新增源 checklist 中包含"检查 RSS 字段完整性" |

#### 6. 36氪财经噪音泄漏

| 维度 | 说明 |
|------|------|
| **现象** | 36氪 RSS 混合了大量财经、股市内容（如"春秋电子股价异常波动"），过滤不彻底 |
| **原因** | 初始的 AI 关键词过滤不够严谨，匹配了部分含 AI 术语的财经文章，且过滤规则是在抓取时实时判断，无法回扫已入库的历史数据 |
| **解决** | 收紧过滤正则，数据库删除 139 条历史噪音数据 |
| **预防** | ① 过滤规则上线后应做一次数据质量检查；② 考虑定期清理（如每天检查当天入库的 36氪数据质量） |

#### 7. AI 关键词子串误匹配（train/again/RAG）

| 维度 | 说明 |
|------|------|
| **现象** | `AI` 匹配了 "tr**ai**n"、"ag**ai**n"、"Pir**ai**te"；`rag` 匹配了 "ga**rag**e"、"d**rag**on" |
| **原因** | 正则缺少 `\b` word boundary，导致关键词被匹配为其他单词的子串 |
| **解决** | 对所有短关键词加 `\b` 边界（`\bAI\b`、`\bRAG\b`），对 .ai 域名用 `(?<!\.)` 负向 lookbehind 排除 |
| **预防** | 正则中的短关键词（≤4 字符）必须加 word boundary，这是一个通用规则，应在代码规范中明确 |

#### 8. Feed 多样性差（GitHub 霸占首页）

| 维度 | 说明 |
|------|------|
| **现象** | 前 20 条几乎全是 GitHub 常青榜/新锐榜/趋势榜，其他数据源无曝光机会 |
| **原因** | GitHub 星数分档 base 过高（100K★=100），即使加 time decay 仍有大量高星仓库占满前排。这是一个多轮迭代才解决的复杂问题 |
| **解决** | 历经 5 轮调整：长青榜封顶 80→70 → GitHub 星数降 5 分 → bonuses 收窄 5→3 → news/podcast base 微调 → 最终实现前 25 条覆盖 6+ 数据源 |
| **预防** | 涉及多数据源排序的算法，应在一开始就设计"多样性保障"机制，而非事后反复调参。例如：同源最多 N 条、类别保底配额 |

### P2 — 代码质量（影响可维护性）

#### 9. 新源 slug→category 映射缺失

| 维度 | 说明 |
|------|------|
| **现象** | 5 个 V1.1 新源在 `fetcher.ts` 中没有 slug→category 映射，使用了默认的 `source.category` 算热度，与 `heatScore.ts` 中的专门 case 不一致 |
| **原因** | `heatScore.ts` 中加了 switch case，但 `fetcher.ts` 中的映射表忘了同步。这是同一个功能在两层文件中的映射逻辑未统一维护 |
| **解决** | 补充 5 个新源的 slug 映射 |
| **预防** | ① 这类"两处同步"的映射关系应该提取为共享常量或函数；② 或者改为统一的映射配置表，而不是两处各自的 if/switch |

#### 10. Tag bonus 重复累加

| 维度 | 说明 |
|------|------|
| **现象** | `fetcher.ts` 中在 `calculateHeatScore()` 之后又手动判断 `tagCount ≥ 3` 做 `hot_score + 5`，而 `calculateHeatScore` 内部已有相同的 bonus 逻辑 |
| **原因** | V1.0 的代码中，`calculateHeatScore` 没有 tagCount 参数，bonus 是在 fetcher 里手动加的。V1.1 重构热评分时将 bonus 移入了 `calculateHeatScore`，但 fetcher 中旧的加分代码没删除 |
| **解决** | 删除 fetcher.ts 中的手动加分块 |
| **预防** | 重构后应 grep 搜索旧逻辑的痕迹是否在别的文件中还有残留 |

#### 11. HN 过滤正则过于宽泛

| 维度 | 说明 |
|------|------|
| **现象** | `intelligence` / `autonomous` / `vision` / `analytics` 等通用词放在 HN 正则中，导致大量非 AI 内容通过过滤（如 business intelligence、vision board、data analytics） |
| **原因** | 初始设计时倾向于"宁可放过不可误杀"，正则偏宽松。且 36氪是中文环境有天然屏障，HN 是纯英文环境泛词匹配率极高 |
| **解决** | 剔除泛词，改用 LLM/GPT/Claude/ChatGPT/OpenAI 等精准关键词组合 |
| **预防** | 英文环境的过滤正则必须比中文更严格，因为英文通用词和 AI 术语词重叠度更高。建议英文过滤用"核心关键词"（模型名+公司名+专有名词）而非"描述性词汇" |

#### 12. 管理员登录无 Token 验证

| 维度 | 说明 |
|------|------|
| **现象** | 任何长度 ≥ 4 的字符串都能进入管理面板 |
| **原因** | `handleLogin` 直接信任本地输入，没有发请求到后端验证 |
| **解决** | 先调 `/api/admin/stats` 验证，403 时计入失败次数，3 次锁定 |
| **预防** | 鉴权相关的逻辑必须走后端验证，前端只是展示层 |

#### 13. 长青榜封顶遗漏批量重算路径

| 维度 | 说明 |
|------|------|
| **现象** | `reheatAll()` 和 `scoreArticle()` 没有应用 evergreen cap 70°C，只有最初抓取时的 `insertRepo` 有 cap |
| **原因** | cap 逻辑只放在了数据入口处（insertRepo），没有在"全量重算"和"单篇重算"路径上加 |
| **解决** | 在 `scoreArticle()` 和 `reheatAll()` 中均添加 cap 检查 |
| **预防** | "封顶/阈值类"逻辑必须覆盖所有写入口：insert → update → batch update。建议用一个统一的 `applyCap()` 函数在热评分计算后调用，而不是在各处手动 if |

#### 14. Cron 时区注释歧义

| 维度 | 说明 |
|------|------|
| **现象** | 常青榜 cron `'0 0 * * 1'` 注释只写"每周一 8:00 UTC+8"，没有说明 UTC 映射关系 |
| **原因** | node-cron 默认使用系统时区（Render = UTC），其他人都按这个假设写表达式，但没在注释中说明 |
| **解决** | 统一加注释 `（cron 使用 UTC：0 0 = 周一 0:00 UTC = 8:00 UTC+8）` |
| **预防** | 所有 cron 表达式必须标注对应的 UTC+8 时间，避免服务器时区变化导致执行时间偏移 |

#### 15. 构建错误（缺括号）

| 维度 | 说明 |
|------|------|
| **现象** | build 报错 `error TS1005: '}' expected` — `gitHubBase` 函数缺少闭合大括号 |
| **原因** | 编辑时删除了 gitHubBase 函数的 `}`，tsc 编译时报错 |
| **解决** | 补回缺失的括号 |
| **预防** | 修改代码后应 build 一次再提交。这是一个基础的质量门禁 |

## 二、Token 消耗分析

### 2.1 V1.1 Token 消耗高的原因

| 原因 | 说明 | 估算占比 |
|------|------|---------|
| **Feed diversity 多轮调参** | 5 轮 base/bonus/star tier 调整，每轮完整循环（分析→改代码→构建→部署→验证→讨论结果） | ~30% |
| **Bug 修复上下文重建** | 部署后发现的 bug 需要重新加载文件、理解上下文、修复、再部署 | ~20% |
| **文档同步** | PRD/AGENTS/RESEARCH/CHANGELOG/RELEASE_NOTES 五处同步更新 | ~15% |
| **验证确认** | 每轮改完等用户 review 反馈，来回确认 | ~15% |
| **功能开发** | 翻译/GitHubHistory/置顶/Admin 等功能本身 | ~15% |
| **git 操作** | 提交、推送、重试等 | ~5% |

### 2.2 优化方向

| 优化 | 具体措施 | 预期效果 |
|------|---------|---------|
| **批量修复模式** | 积累问题清单 → 一次性修复多个 → 统一构建部署 → 统一验证。取代"发现一个修一个"的串行模式 | 减少 50% 的构建-部署-验证循环次数 |
| **本地验证前置** | 修改后先本地 build + curl 测试，确认无误再推送部署。避免部署后才发现低级错误（缺括号、字段缺失等） | 减少 30% 的修复轮次 |
| **文档集中更新** | 功能开发阶段不更新文档，全部完成后一次性更新。文档改动本质上不产生用户价值，可以延后 | 减少 ~15% token（文档同步） |
| **计划先行** | 改代码前先列出"受影响文件清单"+"修改要点"+"潜在风险"，用户确认后再执行。避免中途发现遗漏需要补改 | 减少 20% 的返工 |
| **减少确认轮次** | 对于确定性的修改（如 schema 缺字段），改完直接列出结果，不需要等用户说"好"再继续 | 减少 10% 的来回确认 |

### 2.3 估算：如果按优化模式重做 V1.1

```
当前消耗：~100%（基准）
优化后预期：~55-65%
  其中：功能开发 ~15%（不变）
        批量修复 ~15%（从 20% 降至 15%）
        验证确认 ~10%（从 15% 降至 10%）
        文档集中 ~5%（从 15% 降至 5%）
        减少调参轮次 ~15%（从 30% 降至 15%）
```

## 三、沟通复盘

### 3.1 问题辨识

用户反馈的两类感受是真实的：

**感受一："忘记了之前说过的话"**

具体表现：
- 置顶贴排序问题：用户一开始就说了"置顶应该在最上面"，但我在 PATCH 实现时没有做 `ORDER BY` 的对应调整
- 长青榜封顶：用户说了"长期推荐不霸榜"，但我在 `reheatAll()` 和 `scoreArticle()` 中漏掉了 cap
- feed diversity 调整：每一轮调参后用户说了新的诉求，但下一轮我有时记不住上一轮已经试过的方案

**感受二："新逻辑直接覆盖了旧逻辑"**

具体表现：
- tag bonus 重复累加：V1.1 重构时将 bonus 逻辑移入 `calculateHeatScore`，但旧的 fetcher 加分代码没删
- HN 过滤正则多轮修改中，部分修改未经确认直接替换

### 3.2 根因分析

| 根因 | 机制 | 影响 |
|------|------|------|
| **长上下文衰减** | 对话持续数小时后，早期（2h+前）的决策在 context 中被压缩，后续回复时我可能只以最近的几轮对话作为判断依据 | 遗漏早期已确认的需求细节 |
| **单文件视角** | 修改一个文件时，容易聚焦于该文件的局部逻辑，忽略其他文件中的关联逻辑 | 两处不同步的 bug（slug 映射、bonus、封顶） |
| **确认不足** | 涉及已有逻辑变更时，应该先说明"这会影响 X 行为"再改，但我有时直接动手了 | 用户看到意料之外的改动 |
| **决策未持久化** | 很多共识只在对话中口头确认，没有被记录到代码注释或记忆系统中 | 后续我无法回溯决策上下文 |

### 3.3 改进方案

| 改进 | 具体做法 | 对应问题 |
|------|---------|---------|
| **修改前声明受影响文件** | 每次修改前列出所有受影响的文件和变更要点，用户确认后再动手 | 单文件视角 / 确认不足 |
| **关键决策写进代码** | 复杂度高的逻辑（如热度评分公式）、需要多处同步的规则（如 slug 映射），在代码中加注释说明"同步修改清单" | 两处不同步 |
| **上下文回顾机制** | 当对话超过 50 轮或涉及之前已讨论过的主题时，主动回顾之前的决策，用"之前我们确认过 X，现在是否还适用？" | 长上下文衰减 |
| **涉及旧逻辑变更时先确认** | 任何对已有行为的修改，先用一句话说明"现在的行为是 X，将改为 Y，原因是 Z"，等用户确认 | 覆盖旧逻辑 |
| **记忆系统主动写入** | 关键决策、参数、规则写入 memory 文件，而不是只存在对话中 | 决策持久化 |

### 3.4 对你（用户）的建议

沟通是双向的，以下是我认为可以帮助我们更高效协作的建议：

| 建议 | 说明 |
|------|------|
| **复杂需求先用文档对齐** | 涉及多文件修改的需求，可以用 PRD 或设计文档的方式先对齐，我按文档精确执行 |
| **批量反馈** | 积累 3-5 个问题后一次性反馈，比逐个反馈更高效（减少上下文切换） |
| **明确"确认"和"仅供参考"** | 如果你只是随口提一个观察（如"分数是不是偏低了"），可以明确说"先看看，不一定改"，避免我进入无谓的调参循环 |
| **验收清单前置** | 如果 V1.1 一开始就有完整的验收 checklist，很多问题可以在开发阶段发现，而不是部署后 |

## 四、后续改进清单

### 流程改进

- [ ] 新增数据源 checklist：RSS 字段完整性检查 → AI 过滤规则 → slug 映射 → base_score 配置
- [ ] schema 变更流程：schema.sql 先改 → 代码再写 → 同一 commit 提交
- [ ] 封顶/阈值类逻辑：统一使用 `applyCap()` 函数，在所有写入口调用
- [ ] 映射表类逻辑：提取为共享常量/函数，消除两处维护

### 代码规范补充

- [ ] 短关键词正则：≤4 字符必须加 `\b` word boundary
- [ ] CORS 配置：默认值包含生产域名

## 六、翻译功能复盘（2026-06-04 ~ 2026-06-06）

### 背景

V1.1.1（6/4）将翻译引擎从百度切换为腾讯云 TMT，并引入分级翻译策略。部署上线后腾讯发送余量不足 20% 的短信预警，经排查发现多重问题：

| 时间 | 事件 | 影响 |
|------|------|------|
| **6/2** | 接入百度翻译 API，全量翻译所有英文文章 | — |
| **6/4** | **百度翻译额度耗尽**（4 天用光 85 万字符） | 翻译功能完全失效 |
| **6/4** | 切换腾讯云 TMT，实现分层翻译策略 | 控制消耗速度 |
| **6/4** | 部署后本地配额文件重置 | 计数丢失，继续超额消耗 |
| **6/5** | 腾讯发短信警告余量不足 20% | 排查后发现多重问题 |
| **6/5** | 修复：配额迁移到 DB + schema bug 修复 + 阈值收紧 | 问题收敛 |
| **6/5** | 额度耗尽，自动暂停，管理员可手动恢复 | 等待 7/1 重置 |

---

### 问题清单

#### 1. 本地配额文件在 Render 部署后重置

| 维度 | 说明 |
|------|------|
| **现象** | `server/data/translation_quota.json` 在 Render 部署后计数归零，实际已消耗 ~280 万字符，但计数器显示 ~100 万 |
| **原因** | Render 使用**临时文件系统（Ephemeral Filesystem）**，每次部署都会重建。3-4 次部署 × ~100 万字符计数丢失 ≈ 300 万字符的偏差。这是最根本的误判原因 |
| **解决** | 将配额存储从 JSON 文件迁移到 PostgreSQL `translation_usage` 表，采用内存缓存 `usageCache` + 异步 `saveUsageToDb()` 持久化模式 |
| **预防** | Render 的临时文件系统在官方文档中有明确说明。任何持久状态都应当存储在数据库或外部存储中，不应当信任本地文件。后续涉及 Render 部署的应用，必须审查所有本地文件读写操作 |

#### 2. Schema 中 UPDATE 语句每次部署重置翻译状态

| 维度 | 说明 |
|------|------|
| **现象** | 队列反复扫描已跳过的文章（`title_zh = ''`），日志显示大量"skipped"但无实际 API 消耗 |
| **原因** | `schema.sql` 中包含 `UPDATE articles SET title_zh = NULL WHERE title_zh = ''`，意图是 V1.1 上线时的一次性数据迁移，但 schema.sql 在每次部署时都会执行，导致 `''`（已处理/无需翻译）被重置为 `NULL`（未处理） |
| **解决** | 注释掉该 UPDATE 语句，并添加注释说明"一次性迁移，注释避免每部署重置" |
| **预防** | 每次部署都执行的脚本必须保证幂等。一次性迁移不要放在常规 schema 文件中，应单独执行 |

#### 3. 分级翻译策略初始阈值过宽

| 维度 | 说明 |
|------|------|
| **现象** | 腾讯 TMT 500 万字符在 ~3.5 天内耗尽，远低于预期 10 天 |
| **原因** | V1.1.1 初始阈值（≥65 全翻 / ≥40 仅标题）仍过于宽松，加上 backlog 积压了大量未翻译文章，队列一次性消耗巨量配额 |
| **解决** | 收紧为 **≥80 全翻 / ≥60 仅标题 / <60 跳过**；官方博客改为仅翻标题（原为全翻）；Hacker News 仅翻标题 |
| **预防** | 接入翻译第一天就应该设保守阈值，再逐步放宽。初始值应从紧开始 |

#### 4. 翻译队列上限缺失

| 维度 | 说明 |
|------|------|
| **现象** | 队列一次性无限制处理未翻译文章，消耗全部剩余配额后才停止 |
| **解决** | 队列循环中增加每翻译一条前的 `isQuotaExhausted()` 检查 + 单次运行上限 400 条 |
| **预防** | 涉及消耗外部资源（API 配额、数据库连接、内存）的循环，必须有前置检查 + 硬性上限 |

#### 5. 翻译失败后自动暂停，避免空转重试

| 维度 | 说明 |
|------|------|
| **现象** | 腾讯 TMT 月度额度用完后，队列每 10 分钟扫描一次→发现无法翻译→扫描结束，形成无意义的空转循环 |
| **解决** | `rateLimitedTranslate()` 捕获 "used up" / "free amount" 错误时自动调用 `setTranslationPaused(true)`，暂停后队列直接跳过不再扫描。状态持久化到 DB `paused` 列，永不自动重置 |
| **预防** | 涉及外部 API 的异步队列，必须考虑额度耗尽时的优雅降级路径 |

#### 6. 管理员暂停/恢复翻译开关

| 维度 | 说明 |
|------|------|
| **现象** | 额度耗尽后管理员无法快速关闭翻译功能，只能等待代码部署 |
| **解决** | Admin 页面新增翻译状态卡片：当前状态（运行中/已暂停）+ 用量进度条 + 暂停/恢复按钮。状态写入 DB `paused` 列，除非管理员手动修改，否则永不自动重置 |
| **预防** | 涉及外部付费 API 的功能，应当从一开始就提供管理员控制开关 |

## 七、数据源抓取复盘（2026-06-08）

### 问题清单

#### 1. Seed ON CONFLICT DO NOTHING 导致生产库缺少配置更新

| 维度 | 说明 |
|------|------|
| **现象** | sv101 的 fallback_urls 在生产库中为空，尽管 seed.sql 已修改为正确值 |
| **原因** | seed.sql 使用 `ON CONFLICT (slug) DO NOTHING` 确保幂等性，但这也意味着 seed.sql 中的配置变更只在**首次部署**时生效。后续修改 seed.sql 的行内容对已有数据库完全没有影响 |
| **解决** | seed.sql 末尾新增迁移段，使用 `UPDATE ... WHERE slug = '...' AND feed_url <> '...'` 语句更新已有记录。迁移在每次 startup 时自动运行 |
| **预防** | seed.sql 中的 INSERT 语句仅适用于初始建库。对已有记录的配置变更应单独使用 UPDATE 迁移语句。所有 seed 文件中的"值修改"必须同时考虑已有库的迁移路径 |

#### 2. Feed URL 重定向未检测

| 维度 | 说明 |
|------|------|
| **现象** | sv101 主 feed URL 返回 301，OpenAI Blog 返回 307，Google AI Blog 返回 308。fetchFeed 虽然默认跟随重定向，但每次请求都多一次往返，且增加失败风险 |
| **原因** | 接入 RSS 源时直接使用了官方文档中的 URL，没有检查是否有重定向。Express 的 fetch 默认跟随重定向（最多 20 次），所以功能上可用，但稳定性和延迟不是最优 |
| **解决** | 将所有重定向 URL 替换为最终目标 URL，原 URL 降级为 fallback |
| **预防** | 新增或修改 feed URL 时，先用 curl -v 检查是否有重定向，直接使用最终 URL |

#### 3. `last_fetch` 字段语义混淆

| 维度 | 说明 |
|------|------|
| **现象** | 排查时发现 sv101 的 `last_fetch` 显示 5/29，但无法判断是"源死了"还是"源在跑但无新内容" |
| **原因** | sources API 中的 `last_fetch` 实际上是 `SELECT MAX(created_at) FROM articles WHERE source_id = s.id`，即该源最新文章的入库时间，而非真正的抓取时间 |
| **解决** | (未解决) 暂无机制追踪每次抓取的执行时间。需要新增 `last_fetched_at` 字段或单独记录 fetch 日志 |
| **预防** | 排查问题时，`last_fetch` 只能回答"有无新文章入库"，不能回答"抓取有无失败" |

### 根因分析

| 根因 | 表现 | 出现次数 |
|------|------|---------|
| **seed 模式缺陷** | `ON CONFLICT DO NOTHING` 导致已有库配置更新不生效 | 1 |
| **源接入流程缺失** | 接入 RSS 时没检查重定向，导致非最优 URL | 3 |
| **可观测性不足** | 无法区分"抓取成功但无新内容"和"抓取失败" | 1 |

与之前复盘的对比：
- **"多路径遗漏"**（前两次复盘的核心模式）：这次仍然出现同类问题。迁移 SQL 既要覆盖新库（INSERT）也要覆盖已有库（UPDATE），本质上是"两路径同步"问题。
- **新增模式"源接入完整性"**：接入 RSS 源时有一系列检查项（重定向、数据格式、字段完整性），目前靠人工判断，无 checklist。

### 改进方案

| 改进 | 具体做法 |
|------|---------|
| **种子数据变更清单** | 凡涉及修改 seed.sql 中已有数据的行，必须同时添加对应的 UPDATE 迁移语句 |
| **新增源 checklist** | 1️⃣ 验证 feed URL 无重定向 2️⃣ 确认 RSS 字段完整性 3️⃣ 配置 fallback URL 4️⃣ 添加 slug→category 映射 5️⃣ 配置 base_score |
| **抓取时间追踪** | `sources` 表新增 `last_fetched_at` 时间戳列，每次抓取后更新（无论有无新内容），准确区分"空结果"和"抓取失败" |
| **自动重定向检测** | fetchFeed 在获取 RSS 成功后，检查 `response.url` 是否与请求 URL 一致，不一致则输出 warning 日志
